# 实习生实战题库 · upio

> 我们不看简历筛人，看你怎么把一件事做完。
> 选一道题，24 小时，把代码以 PR 的形式提交到这个仓库。我们据此决定要不要约你聊。

## 这是什么

这三道题分别是我们真实业务里三条链路的**缩小版**：内部知识检索（「企业大脑」）、异步任务编排（渲染工作流）、无 API 环境下的消息自动回复（微信侧）。素材全部脱敏合成，仓里自带 mock 服务与评测脚本，你**不需要**我们的任何账号、key 或环境。

每人只做一道。三道题难度相当，选你最有把握做完的。

| 题 | 一句话 | 适合 | 题面 |
|---|---|---|---|
| **E1 迷你企业大脑** | 对约 30 篇内部文档建索引，命令行检索并给出出处 | 喜欢搜索/数据/后端 | [tasks/E1-mini-brain](tasks/E1-mini-brain/README.md) |
| **E2 工作流自动化** | 收 webhook → 提交异步渲染任务 → 轮询 → 通知；n8n 或任意语言 | 喜欢自动化/集成/后端 | [tasks/E2-workflow-automation](tasks/E2-workflow-automation/README.md) |
| **E3 微信消息自动回复** | 用 UI 自动化驱动一个仿微信网页版，读消息、分类、回复 | 喜欢前端自动化/爬虫/RPA | [tasks/E3-wechat-autoreply](tasks/E3-wechat-autoreply/README.md) |

## 怎么做

1. **领题**：在对应题目的 issue 下评论一句「领题」（issue 列表见 [Issues](../../issues)）。这一步记录你的开始时间。
2. **Fork 本仓**，建分支 `task/<题号>-<你的 GitHub 用户名>`，例如 `task/E2-zhangsan`。
3. 代码放在 `submissions/<题号>/<你的 GitHub 用户名>/`，目录名全小写，必须与你的 GitHub 用户名一致。目录里**必须有** `Dockerfile` 和 `README.md`。详见 [CONTRIBUTING.md](CONTRIBUTING.md)。
4. 本地跑评测：`./scripts/eval-local.sh <题号> <用户名>`。
5. 提 PR 到本仓 `main`，按 PR 模板填写。CI 会自动跑公开评测。
6. 我们收到后会在 PR 上评论 `/eval`，触发隐藏用例评测与一轮自动 review，然后人工看。
7. 我们会留 1–3 条修改意见，请在 **48 小时内**改一轮。
8. 通过的话约 30 分钟通话，请你讲讲你的代码。

**截止时间**：从你收到邀请那天算起 5 天。领题晚了没关系，交得早也不加分——我们看的是完成度和过程。

## 规则

- **可以用 AI 工具**（Claude Code、Cursor、ChatGPT……我们自己天天用）。但通话时你要能解释每一个决定。解释不了的代码，等于没写。
- 评测环境**没有任何 LLM key、没有外网账号**。你的方案必须在没有 key 的情况下也能跑；有 key 时更好是加分项。
- 一个 PR 只改自己的目录。改了别的路径，CI 直接红。
- PR **不会被合并**——这是评估通道，不是贡献通道。评审完成后我们会关闭并打标签。
- 语料与 mock 来自真实生产环境的脱敏版，**不保证干净**。请按你对待生产环境的方式对待它们。
- 请不要在提交里放任何真实的 key、token、手机号。

## 怎么评

评分标准公开：[review/RUBRIC.md](review/RUBRIC.md)。五个维度：验收（30）、解决问题（25）、工程质量（15）、沟通与过程（15）、迭代响应（15）。

其中「解决问题」这一项，我们看的是：题目没明说、但真实环境里一定会遇到的问题，你有没有发现、怎么处理、在 README 里怎么写的。**发现了但选择不处理并写明原因，也算发现。**

## FAQ

**Q：可以两道题都做吗？** 不用。做一道做透。

**Q：可以用什么语言？** 任意。评测只认容器接口。

**Q：mock 或评测脚本有 bug 怎么办？** 提 issue 或直接在 PR 里说明。发现评测脚本的 bug 并给出复现步骤，会在「解决问题」里加分。

**Q：我做到一半时间到了怎么办？** 交。写清楚做到哪、没做什么、为什么。一个诚实的半成品比一个看不懂的全成品有价值。

**Q：有问题问谁？** 开一个 [issue](../../issues/new/choose)。我们工作日 24 小时内回。
